# 開発ワークフロー: スクラップ＆ビルド

## 全体像

```
┌─────────┐    ┌─────────┐    ┌───────────┐    ┌──────────┐
│  SPEC   │ →  │  BUILD  │ →  │  AI PLAY  │ →  │  REVIEW  │
│ 仕様書   │    │  実装    │    │ AIプレイ  │    │ レビュー  │
└─────────┘    └─────────┘    └───────────┘    └────┬─────┘
     ↑                              ↑                │
     │        SCRAP（新仕様 NNN+1）  │  FIX / PIVOT   │
     └──────────────────────────────┴────────────────┘
```

## 1. SPEC — 仕様書作成

- `templates/spec-template.md` をコピーして `specs/NNN-name/spec.md` を作る
- 連番 NNN はゲームごとに増える（例: 001-mineforge, 002-xxx）
- 「何が面白いはずか（コアファン仮説）」を必ず1行で書く。レビューはこの仮説の検証になる

## 2. BUILD — 実装

- `games/NNN-name/` に実装。core/render 分離と AIP 実装（docs/ai-interface.md）は必須
- 最小プレイアブル（コアループが1周回る）を最優先。見た目は後回し

## 3. AI PLAY — AIゲーマーによるプレイ

2つの方法を併用する:

### a. ヘッドレスシミュレーション（定量評価）
- `npm run simulate` で戦略ボットが複数シードで自動プレイ
- 生存日数・撃破数・資源獲得量などの指標を出力
- 用途: バランス崩壊・詰み・クラッシュの検出、難易度カーブの計測

### b. ブラウザ実プレイ（定性評価）
- `npm run dev` でサーバを立て、AI（Claude）が `window.__AIP__` 経由で操作
- `__AIP__.takeControl()` → `step(action)` を繰り返し、状態を読みながら意思決定してプレイ
- 用途: 「実際に遊んで面白いか」「操作の手触り」「理不尽さ」の評価
- **ペルソナプレイ**: `personas/pNN-*.md` の人格・評価基準を採用してプレイ＆レビューする。
  複数ペルソナで遊ぶと「誰にとって面白いか」が分離できる。レビューには使用ペルソナを明記する

## 4. REVIEW — レビュー

- `templates/review-template.md` をコピーして `reviews/NNN-name-vX.md` に書く
- 定量データ（シミュレーション結果）と定性所感（実プレイ）の両方を載せる
- 最後に必ず判定を出す:
  - **FIX**: コアは面白い。バグ・バランス修正で改善（同じゲームの vX+1 へ）
  - **PIVOT**: コアの一部を活かして大きく方向転換（同じ番号のまま仕様書を改訂）
  - **SCRAP**: コア仮説が外れた。学び（Learnings）を書き、新番号の仕様書を作る

## 5. 収束

- 複数プロトタイプのレビューが溜まったら、Learnings を横断して
  「最終プロトタイプの仕様書」を作る。これが iPad/Android 移植のベースになる
