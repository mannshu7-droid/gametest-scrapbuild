# スクラップ＆ビルド自動ルーチン仕様

6時間おきに自動実行される開発ルーチンの定義。**4回の実行で1サイクル＝1ゲーム**（1日1ゲームのイメージ）。
実行時の現在位置（何サイクル目・何回目か）は必ずルート直下の `routine-state.md` を読んで判断し、
作業後に更新すること。

## 目的と制約

- **目的**: 最終的に 7 Days to Die のような「戦闘・採掘・建築」を併せ持つゲームを作るため、
  まず**要素を1つに絞ったゲーム**を量産し、各要素の「最も面白いシステム」を発見する。
  最後に最良のシステム同士を組み合わせて本命ゲームを作る
- **1ゲーム = 1要素だけ**: 戦闘だけ / 採掘だけ / 建築だけ。他要素は入れない
- **ゲームシステムの検証が目的**: 面白さ・爽快感・楽しさ・継続できそうか。
  コンテンツ拡張（ステージ数・アイテム種類の水増し等）はしない
- **ターゲット**: iPad/Android（Capacitor移植前提）。仕様書にタッチ操作の想定を必ず書く。
  実装は core/render 分離を守ればキーボード操作でよい
- **今回はシングルプレイのみ**（将来のマルチプレイは仕様書の「スコープ外」に記載だけする）
- 技術規約・AIP・決定論は CLAUDE.md / docs/ai-interface.md に従う

## 要素ローテーション

| サイクル | 要素 |
|---|---|
| 1 | 戦闘（combat） |
| 2 | 採掘（mining） |
| 3 | 建築（building） |
| 4以降 | それまでの Learnings から最も検証価値の高いものを選ぶ（弱かった要素の再挑戦 or 組み合わせ試作） |

## フォルダ規約（要素が分かるように）

- 仕様書: `specs/NNN-<要素>-<名前>/spec.md`（例: `specs/002-combat-slash/spec.md`）
- 実装: `games/NNN-<要素>-<名前>/`（specs と同じ連番・名前）
- レビュー: `reviews/NNN-<要素>-<名前>-vX.md`、最終総括は `-final.md`
- `games/README.md` の索引表（要素・状態・リンク）を毎回更新する
- ※ `001-mineforge` はルーチン導入前の複合プロトタイプ（参考資料扱い）

## 各回の作業内容

### 1回目: BUILD ＋ REVIEW（新ゲーム作成とレビュー）
1. `reviews/` の全 Learnings と `personas/` を読む
2. 今サイクルの要素で仕様書を書く（`templates/spec-template.md` 使用、タッチ操作の想定を含める）
3. `games/NNN-<要素>-<名前>/` に実装（コアループが1周回る最小構成、AIP・simulate 必須）。
   **見た目の最低限（2026-11-24追加）**: `templates/render/sprites.ts` を `src/render/sprites.ts` にコピーして使い、
   自分（人の形）・敵（種類ごとの怪物）・地形（土／石／鉱石など）・建物（柵・砲台・拠点・篝火など）を**単色の円や四角（ドット）だけで描かない**。
   盤面の端に凡例（`drawLegend`）を出す。1マス（または自分の大きさ）は画面で32px以上を目安にする。
   スクリーンショット（Playwright の Chromium）で「どれが自分・敵・土・石か」を見分けられることを確かめ、v1 レビューに一言書く
4. `npm run build` と `npm run simulate` で動作確認
5. **P01（野望型）と P02（あき型）の両ペルソナでプレイ**（simulate＋可能ならブラウザAIP）し、
   各ペルソナの評価基準・ネガティブ基準で採点、改善点を列挙して `reviews/NNN-…-v1.md` を書く

### 2回目: FIX ＋ REVIEW（修正と再レビュー）
1. v1 レビューの改善点を修正する（優先度順、全部でなくてよいが致命・重大は必須）
2. build / simulate で確認後、修正版を両ペルソナで再プレイ
3. 再評価と残改善点を `reviews/NNN-…-v2.md` に書く（v1 からの改善差分を明記）

### 3回目: FIX only（修正のみ）
1. v2 レビューの改善点を修正する
2. build / simulate で確認する（レビューは書かない。修正内容は PR 本文に記載）

### 4回目: FINAL REVIEW（総括レビュー）
1. 最終版を両ペルソナでプレイし、`reviews/NNN-…-final.md` を書く。内容:
   - ゲームとしてのトータル評価（両ペルソナの軸別採点＋総合判定 FIX/PIVOT/SCRAP）
   - この要素のシステムとして「本命ゲームに採用すべき部分・捨てる部分」
   - **次にどのようなゲームを作ればよいか**（次サイクルへの具体的提案）
2. **スマホで動作確認できるページを作って公開する**（2026-11-20追加）:
   - ゲームのフォルダに `mobile.json`（観戦できる戦略・タッチのボタンの割り当て・短い遊び方。書式は `games/036-flagship-trodvent/mobile.json`）を置き、
     `node tools/mobile-html.mjs games/NNN-…` で `mobile/NNN-….html` を作る（ゲーム本体は変えない外付けのページ。ボット観戦×1〜×16とタッチ操作）
   - **Artifact の公開は必須**（2026-11-24: クラウドのルーチンにも Artifact ツールがあることを確認した）。そのファイルを Artifact として公開し
     （`routine-state.md` や `games/README.md` に既に URL があるゲームはその URL へ更新）、URL を final レビューの冒頭・`games/README.md` の行・PR 本文・`routine-state.md` に書く
   - 公開前に Playwright の Chromium（スマホの画面サイズ）でページを開き、ボット観戦が動いてエラーが無いこと、盤面の絵が見分けられることを確かめる
   - Artifact ツールが本当に無い環境に限り `mobile/NNN-….html` をコミットするだけにし、`routine-state.md` の備考に
     「スマホ確認ページ未公開: mobile/NNN-….html」と書く。次に Artifact を使える環境で動いた回（または人の手元のセッション）が公開して備考を消す
   - 外部への公開（GitHub Pages 等）はしない
3. `routine-state.md` を次サイクル（次の要素・run 1）に更新する

## クラウドのルーチンで動かす時の注意（2026-11-20追加）

このルーチンは claude.ai のクラウドのルーチン（Linux のサンドボックス、リポジトリを毎回クローン）でも動く。手元の Windows との違い:

- **ブラウザペインは無いが、Playwright の Chromium がある**: `node tools/single-html.mjs` の単一HTMLに
  `npx esbuild headless/simulate.ts --bundle --format=iife --global-name=__BOTLIB__` のボットを埋め込んで `__AIP__` で3ランを回し、ヘッドレスと一致することとスクリーンショット（盤面の絵が見分けられるか）を確かめる。
  レビューには「ブラウザペインの代わりに Playwright Chromium で実施」と書く
- **Artifact ツールはある**: 4回目のスマホ確認ページは公開まで行う（上の4回目の2.）
- **並列数は `nproc` に合わせる**（手元は21並列。クラウドは少ないことが多いので、160シード×5条件の全グリッドが時間内に終わらない時は 1〜80 の2組に絞り、絞ったことをレビューに書く）
- 一時ファイルは `/tmp` ではなくリポジトリの外の作業用ディレクトリ（例: `$HOME/work`）に置き、コミットしない
- `npm install` は各ゲームのフォルダで最初に1回（`node_modules` はクローンに含まれない）
- PR の作成・マージは `gh` が使えればそれで行う。使えない場合はブランチを push し、PR 作成・マージの代わりに使えるツール（GitHub の連携）で行う。
  どちらもできなければ push までで止め、`routine-state.md` を更新した同じブランチに残して、結果の要約に「未マージ」と書く
- 手元のローカル定期タスク（scrapbuild-game-cycle）は二重実行を避けるため無効にしてある

## 毎回必ず行うこと（Git）

1. 開始時: `git checkout main && git pull` で最新化
2. 作業ブランチを切る: `cycle<N>-run<M>-<内容>`（例: `cycle1-run1-build-combat`）
3. 作業後: コミット → push → `gh pr create` で PR 作成（本文に作業内容の要約）
4. `gh pr merge --squash --delete-branch` で main へマージ
5. `routine-state.md` の更新（実行履歴の追記）も同じ PR に含める

リポジトリ: https://github.com/mannshu7-droid/gametest-scrapbuild

## 失敗時の扱い

- ビルドが壊れている等で本来の作業に入れない場合: まず直すことを優先し、PR 本文に経緯を書く
- 1回の実行で作業が終わりきらない場合: 完了した分だけでも PR/マージし、
  `routine-state.md` の備考に残作業を書く（次回実行が引き継ぐ）
