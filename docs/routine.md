# スクラップ＆ビルド自動ルーチン仕様

6時間おきに自動実行される開発ルーチンの定義。**4回の実行で1サイクル＝1ゲーム**（1日1ゲームのイメージ）。
実行時の現在位置（何サイクル目・何回目か）は必ずルート直下の `routine-state.md` を読んで判断し、
作業後に更新すること。

## 目的と制約

- **目的**: 最終的に 7 Days to Die のような「戦闘・採掘・建築」を併せ持つゲームを作るため、
  まず**要素を1つに絞ったゲーム**を量産し、各要素の「最も面白いシステム」を発見する。
  最後に最良のシステム同士を組み合わせて本命ゲームを作る
- **1ゲーム = 1要素だけ**: 戦闘だけ / 採掘だけ / 建築だけ。他要素は入れない
- **ゲームシステムの検証が目的**: 面白さ・爽快感・楽しさ・継続できそうか。
  コンテンツ拡張（ステージ数・アイテム種類の水増し等）はしない
- **ターゲット**: iPad/Android（Capacitor移植前提）。仕様書にタッチ操作の想定を必ず書く。
  実装は core/render 分離を守ればキーボード操作でよい
- **今回はシングルプレイのみ**（将来のマルチプレイは仕様書の「スコープ外」に記載だけする）
- 技術規約・AIP・決定論は CLAUDE.md / docs/ai-interface.md に従う

## 要素ローテーション

| サイクル | 要素 |
|---|---|
| 1 | 戦闘（combat） |
| 2 | 採掘（mining） |
| 3 | 建築（building） |
| 4以降 | それまでの Learnings から最も検証価値の高いものを選ぶ（弱かった要素の再挑戦 or 組み合わせ試作） |

## フォルダ規約（要素が分かるように）

- 仕様書: `specs/NNN-<要素>-<名前>/spec.md`（例: `specs/002-combat-slash/spec.md`）
- 実装: `games/NNN-<要素>-<名前>/`（specs と同じ連番・名前）
- レビュー: `reviews/NNN-<要素>-<名前>-vX.md`、最終総括は `-final.md`
- `games/README.md` の索引表（要素・状態・リンク）を毎回更新する
- ※ `001-mineforge` はルーチン導入前の複合プロトタイプ（参考資料扱い）

## 各回の作業内容

### 1回目: BUILD ＋ REVIEW（新ゲーム作成とレビュー）
1. `reviews/` の全 Learnings と `personas/` を読む
2. 今サイクルの要素で仕様書を書く（`templates/spec-template.md` 使用、タッチ操作の想定を含める）
3. `games/NNN-<要素>-<名前>/` に実装（コアループが1周回る最小構成、AIP・simulate 必須）
4. `npm run build` と `npm run simulate` で動作確認
5. **P01（野望型）と P02（あき型）の両ペルソナでプレイ**（simulate＋可能ならブラウザAIP）し、
   各ペルソナの評価基準・ネガティブ基準で採点、改善点を列挙して `reviews/NNN-…-v1.md` を書く

### 2回目: FIX ＋ REVIEW（修正と再レビュー）
1. v1 レビューの改善点を修正する（優先度順、全部でなくてよいが致命・重大は必須）
2. build / simulate で確認後、修正版を両ペルソナで再プレイ
3. 再評価と残改善点を `reviews/NNN-…-v2.md` に書く（v1 からの改善差分を明記）

### 3回目: FIX only（修正のみ）
1. v2 レビューの改善点を修正する
2. build / simulate で確認する（レビューは書かない。修正内容は PR 本文に記載）

### 4回目: FINAL REVIEW（総括レビュー）
1. 最終版を両ペルソナでプレイし、`reviews/NNN-…-final.md` を書く。内容:
   - ゲームとしてのトータル評価（両ペルソナの軸別採点＋総合判定 FIX/PIVOT/SCRAP）
   - この要素のシステムとして「本命ゲームに採用すべき部分・捨てる部分」
   - **次にどのようなゲームを作ればよいか**（次サイクルへの具体的提案）
2. `routine-state.md` を次サイクル（次の要素・run 1）に更新する

## 毎回必ず行うこと（Git）

1. 開始時: `git checkout main && git pull` で最新化
2. 作業ブランチを切る: `cycle<N>-run<M>-<内容>`（例: `cycle1-run1-build-combat`）
3. 作業後: コミット → push → `gh pr create` で PR 作成（本文に作業内容の要約）
4. `gh pr merge --squash --delete-branch` で main へマージ
5. `routine-state.md` の更新（実行履歴の追記）も同じ PR に含める

リポジトリ: https://github.com/mannshu7-droid/gametest-scrapbuild

## 失敗時の扱い

- ビルドが壊れている等で本来の作業に入れない場合: まず直すことを優先し、PR 本文に経緯を書く
- 1回の実行で作業が終わりきらない場合: 完了した分だけでも PR/マージし、
  `routine-state.md` の備考に残作業を書く（次回実行が引き継ぐ）
