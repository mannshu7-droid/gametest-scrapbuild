## 今回の変更範囲

cycle12-v1の残課題（実機・可視ブラウザでのD-pad/ボタンの見た目・触感の最終確認）に対応するため、
routine-state.mdの指示通りBrowser paneを表示した状態での`screenshot`取得を試みた。結果は
前回と同じく「pane is not displayed」でタイムアウトし続け、本セッションでは画像による見た目確認は
今回も実施できなかった（詳細は下記「環境制約の確認」）。ただし、`screenshot`が使えない代わりに
**DOM実測（`getBoundingClientRect`によるジオメトリ解析）で「見た目」に相当する問題を具体的に2件
発見し、両方とも修正した**。これはcycle12-v1が実施した「Action変換ロジックの正しさ」の検証とは
別の観点（レイアウトが実際の画面サイズに収まるか）であり、v1では未検証だった領域である。

- 変更1: `index.html` — canvasの表示サイズを固定px（384×600+border、iPhone等375px幅の画面では
  横に約11pxはみ出す）から、`max-width`/`max-height`とアスペクト比維持のCSSでビューポートに
  収まるよう縮小表示するよう変更（内部解像度=`canvas.width/height`は不変、描画は従来通り鮮明）。
  タッチオーバーレイ（`TouchInput`のD-pad・ボタン）はcanvasを包む`wrap`要素のサイズに追従する
  実装のため、この変更だけで自動的に画面サイズへ追従するようになった
- 変更2: `src/render/touchInput.ts` — 画面幅が狭い横向き（例: スマホの横持ち）でcanvasが高さ基準に
  大きく縮小されると、D-pad（wrap幅の28%）とアクションボタン（固定160px幅）が同じ行に収まらず
  重なることを実測で発見。実際に重なりが発生する条件を毎tick判定し、発生時のみ「画面が狭すぎて
  操作ボタンが重なっています。端末を縦向きにするか、画面を広げてください。」という通知オーバーレイを
  表示するようにした（レイアウト自体を横向き対応させる改修はスコープ外と判断、詳細は後述）
- **`src/core/game.ts`は無変更**（想定通り。ゲームロジック・バランス検証への影響はゼロ）

## 環境制約の確認（cycle12-v1のLearningsの再検証・更新）

cycle12-v1は「Browser paneが非表示状態だと`screenshot`が失敗する」ことを報告し、次回は表示された
状態で試すことを推奨していた。今回もセッション開始時から`screenshot`は一貫して
「the Browser pane is not displayed, so the page is not compositing frames」で失敗し続けた
（本自動ルーチンはユーザー不在で実行されるため、pane が可視状態になることはない構造的な制約と
判断する）。

今回はこの制約の実際の影響範囲をより正確に切り分けた:

| 操作 | 結果 | 備考 |
|---|---|---|
| `screenshot` | 失敗（タイムアウト） | 既知（cycle12-v1で確認済み） |
| `computer`の座標指定クリック・`left_click_drag` | 失敗（"requires a prior screenshot"） | 新規判明。座標系キャッシュが無いため実行不可 |
| `computer`の`ref`指定クリック（要素参照） | **エラーは出ず成功したように見えるが、実際にはDOMへ何もイベントが届いていない** | 新規判明。詳細は下記 |
| `read_page` / `javascript_tool`によるDOM読み書き | 正常動作 | cycle12-v1と同じ |

3番目の項目が今回新たに判明した重要な事実である。`document`に`pointerdown`/`pointerup`/`click`の
グローバルリスナーを仕込んだ上で`computer.left_click(ref)`を実行したところ、ツール呼び出し自体は
「left_click at (x,y) [ref]」と成功を報告するが、**3種のイベントいずれもカウントが0のまま**だった。
さらに、購入可能な状態（所持金25、コスト15の積載拡張カード）に対して同じ`ref`クリックを2回実行しても
所持金・maxCapacityとも一切変化しなかった。一方、同じ要素へ`PointerEvent`を`dispatchEvent`で
直接発火する方式（cycle12-v1の手法）は同条件で正しく購入を成立させた（所持金25→10、
maxCapacity20→25、下記「技術検証」参照）。

これにより、cycle12-v1が「screenshotが失敗するので実機操作の確認ができない」としていた制約は、
実際には**`screenshot`だけでなく`computer`ツールによる実際の入力送信そのものが、paneが
非表示のセッションでは機能しない（エラーにならず静かに無効化される）**という、より広い制約
だったことが判明した。したがって「可視ブラウザでのタップ・ドラッグによる実操作確認」は、
ユーザー不在で実行される本自動ルーチンの構造上、原理的に実施不可能である（paneを可視化できる
のはユーザーが対話的にセッションを開いている場合のみ）。この結論はLearningsに記載し、
次回以降は同じ検証を試みる代わりに、DOM実測とsynthetic PointerEvent検証（cycle12-v1の手法）を
「見た目」の検証にも拡張する方針へ切り替えるべきと判断した。

### ジオメトリ実測（修正前後の比較）

`getBoundingClientRect()`でcanvas・D-pad・ボタン群の描画位置を4種のビューポートで実測した。

| ビューポート | 修正前 | 修正後 |
|---|---|---|
| モバイル縦 375×812 | canvas横幅385.3px（画面幅381pxを4px超過、左端が-5pxでクリップ） | canvas 361×562.9pxに収まり、右端368px・下端667pxとも画面内（余白: 右7px・下145px） |
| タブレット 768×1024 | （未計測） | canvas 386×602px（原寸のまま、中央配置、画面内に収まり余白十分） |
| スマホ横向き相当 812×375 | canvas高さ基準で216.4×337pxに縮小、**D-pad右端376.4pxとボタン群左端338.2pxが38px分重なる** | 同じ縮小は起きるが重なりを検出し「画面が狭すぎる」オーバーレイを表示（rotateDisplay: "flex"） |
| デスクトップ 1280×800 | （元々問題なし） | オーバーレイは非表示のまま（rotateDisplay: "none"）で影響なし |

修正前のモバイル縦表示での「4px程度のクリップ」自体は軽微だが、実機の画面幅は端末により
375px未満のもの（例: 一部の旧型Android）もあり得るため、固定pxレイアウトのまま実機へ展開すると
機種によってD-padの左端やボタンの右端が画面外に出て**タップ不能になるリスク**があった。
また「スマホ横向き」のケースは実際に操作ボタンの物理的な重なりを引き起こしており、
修正しなければ横持ちでプレイした場合にD-padの一部がボタンに覆われてタップ不能になっていた
（このゲームは仕様上ずっと縦シャフトを掘り進める構成のため縦持ちが本来の想定操作だが、
仕様書にその明記がなかったため今回追記した。下記「Learnings」参照）。

### P01（野望型）視点

- 効率重視のP01にとって、修正1（canvas responsive化）は「見えないコスト」を取り除く修正である。
  固定pxレイアウトのままだと、画面幅の狭い端末ではD-padやボタンの一部が画面外にはみ出し、
  本人が気づかないまま反応が鈍る（はみ出た領域はタップしても反応しない）状態になり得た。
  これはP01の評価基準A2（成長実感・パワーカーブ）の前提となる「操作した分だけ確実に結果が
  返ってくる」体験を静かに損なう類のバグであり、修正の優先度は高いと判断できる
- 修正2（横向き重なり検出）はP01の主な評価軸ではないが、少なくとも「操作不能なのに何の
  フィードバックもない」状態（N3停滞に近い理不尽さ）を回避できている点は評価できる

### P02（あき型）視点

- 修正2（横向き重なり検出）はP02の最重要軸A9（世界の一貫性・干渉自由度、「ちゃんとしてる」
  体験）に直結する。ボタンが黙って重なって反応しない状態は「説明のつかない挙動」（A9の
  ネガティブ基準）そのものであり、代わりに明示的な日本語メッセージで理由を説明する設計は
  A9が求める一貫性・誠実さのパターンに合致する
- 修正1・2ともB6（操作性・手触り、P02では★★★の中重み軸）に直接関わる。「操作が意図と
  噛み合わない」（B6のネガティブ基準）状態を、画面サイズに関わらず起こりにくくした点は
  ポジティブに評価できる
- 一方でN13（P02における「細かい操作の空振り」軸）の核心である「実際の指でのドラッグ操作の
  レイテンシ・誤タップ率」は、今回も環境制約（上記）により未検証のまま残った。これは
  cycle12-v1から持ち越された唯一の未解消項目である

## 判定

**FIX**

理由: cycle12-v1の残課題（見た目確認）に対しスクリーンショットでの直接確認は環境制約により
今回も不可能だったが、代替手段（DOMジオメトリ実測）によって「見た目」に相当する実害のある
問題（画面クリップ・ボタン重なり）を具体的に2件発見し、両方とも致命・重大として修正した。
`npm run build`・`npm run simulate`とも成功、コアロジックへの影響はゼロ。残る未解消項目
（実機の指ドラッグの触感）は本セッション固有の環境制約による構造的な限界であり、次回以降の
ヘッドレス自動実行でも同じ制約に直面する可能性が高い（Learnings参照）。

## Learnings（次の仕様書・実行に持ち越す学び）

- **`screenshot`が失敗するBrowser paneセッションでは、`computer`ツールの`ref`指定クリックも
  実際にはDOMへイベントを届けない（エラーは返らず「成功」と表示されるため気づきにくい）。**
  今回、グローバルイベントリスナーのカウントと実際の状態変化（所持金の増減）の両方で
  「クリックが届いていないこと」を直接証明した。座標指定のクリックやドラッグは
  「screenshotが必要」と明示的にエラーを返すため気づきやすいが、`ref`指定クリックは
  静かに空振りするため要注意。この制約はユーザー不在の自動ルーチン実行では原理的に
  回避できないため、今後タッチ操作の「実際の入力パイプラインでの動作確認」を行う際は
  cycle12-v1・v2で確立した「DOM実測＋synthetic PointerEvent dispatch」を標準手法とし、
  `computer`ツールでの実クリック再現は試みるだけ時間を消費すると理解した上で早めに切り上げる
- **canvasのようなfixed-pixel解像度で描画するCanvas 2Dゲームは、CSSの`max-width`/`max-height`
  ＋`width:auto`/`height:auto`（img要素と同じ「responsive image」パターン）でアスペクト比を
  保ったまま表示サイズだけを画面に収める、という定石が内部解像度を変えずに実機対応できる
  最小コストの方法だった。タッチオーバーレイ（D-pad等）がcanvasの「描画サイズ」を包む
  wrap要素基準で配置されている設計（cycle12-v1）のおかげで、この変更だけで自動的に
  オーバーレイもレイアウト追従した。今後Capacitorでのネイティブビルドに進む際もこの
  パターンを維持すべき
- D-pad（%指定）とボタン群（固定px指定）を画面の両端に配置する設計は、画面が十分広ければ
  問題ないが、極端に狭い横向き画面では両者が算術的に必ず重なる（本レビューの計算式参照）。
  今回は「重なりを検知して警告する」対症療法にとどめ、レイアウト自体の横向き対応
  （D-pad/ボタンを縮小する、配置を変える等）はスコープ外とした。本ゲームは縦シャフトを
  掘り進める構成上、縦持ちプレイが自然な前提であり、spec.mdに「想定操作方向は縦持ち、
  横持ちは非対応（画面が収まらない場合は警告を表示）」と明記した。将来的にiPadでの
  横持ち利用を正式サポートする場合は、この警告オーバーレイをレイアウト再設計に置き換える
  必要がある
