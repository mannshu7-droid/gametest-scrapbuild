## v1からの変更点

v1バグ#1（全力投資の多脚が brace 単体に-31.2%で負ける）を調べた結果、数値の大小ではなく構造の問題だった。

1. **接続1本では基礎保護（高さ≤3）直上の1ブロックしか楽にならない**。接続は「その高さより上の重量」を
   分けるだけなので、高さ4で繋いでも中央の高さ5以上は単一柱のまま
2. **3本を同じ高さまで建てると、各列がそれぞれ自分の重さを背負う**。重さを本数で割るだけでは単一柱の
   上限を越えられない（静的な負荷計算で確認: 石だけの中央を高さ12まで積むと最下部の負荷率3.3。v2の作業途中で試した弱めのトラス係数0.4でも、石3本を梁3段ごとに繋いだ構造は1.1〜1.5で崩れる）
3. **脚を建てても収入ゼロ**。収入は中央の到達高度マイルストーンだけで、脚の資材費はまるごと持ち出し

また v1 の「脇脚は`LEG_WIND_OFFSET`のせいで自壊する」という分析（バグ#2）は誤りだった。高度バンド0の風係数は
+5%にすぎず、脇脚が高さ9に届かない本当の理由は「素の石柱は自重で7前後が上限」という単一柱の物理そのもの。

これを受けて以下を変更した（数値だけの調整では直らないため、接続の仕組み自体を作り直した）。

| 変更 | 内容 |
|---|---|
| 梁を複数架けられる | `connect`は「その脚の唯一の接続を上書き」から「その高さに梁（rung）を1本追加」へ。`LegSummary.rungs`で一覧を公開 |
| トラス効果 | 梁の高さでは中央＋その高さに梁がある脚の上方荷重を合算し、`TRUSS_FACTOR`（脚1本0.5／2本0.35）を掛けて均等に再分配 |
| 梁が横揺れを止める | 梁から上下2マス以内は揺れ半減（`RUNG_SHAKE_RADIUS`）。最上段の梁より下では脇脚の風オフセットが消える |
| 梁が足場になる | 梁の高さでは脚〜中央の間を横移動できる（地上へ降りずに列を渡れる） |
| 脚にもマイルストーン報酬 | 左右の脚も中央と同じ式で、高さ3ごとに報酬（`LEG_MILESTONE_RATIO`=1.0） |
| `BEAM_COST` | 25→8（梁を何段も架ける前提） |
| `TIME_LIMIT` | 3600→7200。10tpsで6分しかなく、仕様書の想定セッション8〜15分と食い違っていた |

検証ボット側でも、全戦略に影響するバグを2件直した。

- **地上で資材もbraceも無いのに柱へ登っては降りる往復**（v1で直した往復バグの地上起点版）。労働収入が半減していた
- **tripodCarefulが鑑定をbraceより先に買っていた**。序盤にbraceが買えず崩落を繰り返し、マイルストーン収入が止まっていた。
  v1でtripodCarefulが負けた主因の一つはこれだった

戦略も梁の仕組みに合わせて組み直した。twin/tripodは高さ4から2段ごと、tripodCarefulは高さ6から3段ごとに
「中央→各脚→梁」を繰り返す。新設の`tripodOnce`は高さ4に1本だけ架ける、v1のtripodと同じ診断用ボット。

## 判定

**FIX**

理由:

- コアファン仮説「多脚で単一支柱の頭打ちを突破できる」は、**平均と安定性の面では成立した**。全力投資の
  多脚が brace 単体を上回り（+8.8%、40到達17/20 vs 12/20）、単一柱が立ち上げに失敗するシードの大半を
  救っている。v1の「頑張って組み合わせたのに損をする」逆転は解消
- 一方、本作のもう一つの柱「どこで・いつ繋ぐかという悩ましい選択」は、早く・密に編むのが唯一の正解に
  なっており成立していない（新規#1）。脚のマイルストーンによる収入の膨張（新規#2）も、投資判断の
  面白さを薄めている
- いずれも梁の仕組み自体（多段の梁・トラス・揺れ半減・足場）は健全で、数値と報酬設計の調整範囲の課題。
  PIVOT／SCRAPの段階ではない

## Learnings（次の仕様書・v3に持ち越す学び）

- **「重さを分ける」だけでは、分けた先の構造物にも同じ自重の問題がある限り上限を越えられない**。荷重分散を
  売りにするシステムは、分散そのものに上乗せの効果（トラス係数・揺れ止め）を持たせないと、本数を増やしても
  単一柱と同じ壁に当たる。今回は静的な負荷計算（列を手で組んでcomputeStressだけを呼ぶ）で数分で確かめられた。
  数値調整に入る前に、この種の「理想配置での上限」を先に計算すべきだった
- **検証ボットのバグが、比較対象（対照群）の数字まで歪めていることがある**。v1・019で「単一柱の頭打ち」と
  呼んでいた現象の大半は、ボットの往復バグで労働収入が半減していた影響だった。新システムと既存システムを
  比較するときは、対照群のボットの行動ログも一度は読むべき
- **新システムが「上限を伸ばす」のか「失敗の保険になる」のかは、平均ではなくシードごとの分布で見ないと
  分からない**。平均+8.8%の裏で、単一柱は全か無か、多脚は連続的という全く違う性格をしていた
- **セッション長は評価の前提そのもの**。3600tickでは多脚は損（30.4 vs 46.4）、7200tickでは得（65.2 vs 59.9）。
  「時間をかけた投資が後で効く」タイプのシステムは、想定セッション長で評価しないと結論が逆になる
- **報酬を「どの列でも同じ」にすると、列の数だけ収入が増える**。建設コストを回収させる仕組みは、脚の本数に
  比例して増えない形（例: 梁で繋がった構造全体の最高高度にだけ報酬、脚の報酬は梁が架かった時点で確定 等）を
  v3で検討する
- 43サイクル連続でブラウザAIP実プレイが未実施。梁の描画や梁の上の横移動が直感的に伝わるかは、ヘッドレスでは
  検証できない（`.claude/launch.json`にport 5192で`rootweave`設定済み）
