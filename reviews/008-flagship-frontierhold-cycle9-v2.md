## 定量評価（ヘッドレスシミュレーション）

### 発見: depth37〜43付近への複数戦略同時貼り付き（20〜27%のシードで発生）

`npm run simulate -- --seeds 101,...,200 --maxTicks 20000`（100シード×8戦略＝800ラン）を実行し、
「ticks=20000完走・死亡なし・maxDepth<45・oreMined<10」を機械的に抽出したところ、198/800ラン
（61シード）が該当した。このうち34シードは`balanced-no-outpost`（前線基地を建てないA/B対照群）
単独の貼り付きで、007以来「前線基地が無いと深く進めない」という設計通りの想定内挙動である。
しかし残り27シードは、前線基地を運用する戦略（mining-first/combat-first/balanced系、
最大7戦略）が**同時に**同じ深さ帯へ貼り付いており、この規模（27/100=27%）は看過できないと判断した。

### 原因調査

`headless/simulate.ts`のrunOne()へ一時トレース機能（tick範囲指定でphase/y/money/fuel/
wallReserve等を出力、調査後に削除済み）を追加し、seed=103・mining-first戦略を追跡した。

判明した機序:

1. depth37→38への掘削（`p.digging`、複数tickかけて完了）が残りわずか（1〜3tick）まで進んだ
   タイミングで、`estFuelToReturn + returnMargin`による帰還安全判定が先に発火し撤退へ切り替わる
2. 撤退のため隣接FLOORへ移動すると`applyMove()`が無条件で`p.digging = null`にするため、
   ほぼ完了していた掘削進捗が丸ごと失われる（004以来の既知パターン「掘削中断で進捗リセット」の
   別形態での再発）
3. この壁の直前まで到達できる燃料容量ちょうどで運用しているシードでは、次のトリップでも
   全く同じ地点で全く同じタイミングで撤退するため、貫通が永遠に発生しない。加えて基地到着直後に
   即座に再潜行してしまい（`minEscapeBridgeCost`は別カラムがdrillPowerで貫通可能なため
   「壁ではない」と正しく判定し`wallReserve`自体が発火しない）、基地滞在中のみ加算される
   LABOR_INCOMEも一切貯まらず、経済が完全に停滞する

**原因は`src/core/game.ts`（ゲーム本体）ではなく`headless/simulate.ts`のBotの帰還判断の
優先順位**であり、実プレイヤーが「あと一歩で貫通」という状況を認識して無理に押すか安全に
撤退するかを自分で判断できるのに対し、検証ボットは機械的な安全マージンだけで判断するため
起きる、検証ボット固有の制約である。

### 修正と検証

`needsReturn`判定に、「掘削残り3tick以下、かつそれを終えてもなお`estFuelToReturn`以上の
燃料が残る」場合に限り安全マージン判定を一時的に無効化する`finishingDigSafely`を追加した。
掘削の実質2倍の燃料消費（移動分+掘削分）と、完了後にさらに1マス深く進むことによる
`estFuelToReturn`の増分の両方を見込んだ余裕（`digging.remaining*2+2`）を要求し、
fuel<=0・満載・低HP・adaptiveRiskRetreatの安全側トリガーは変更していない。

| 指標（100シード×8戦略、seed101〜200） | 修正前 | 修正後 |
|---|---|---|
| depth37〜43への複数戦略同時貼り付き（シード数） | 27 | 17（-37%） |
| 貼り付き総ラン数（198/800中） | 198 | 99（-50%） |
| mining-first avgMaxDepth | 91.9 | 105.4 |
| balanced avgMaxDepth | 81.0 | 100.1 |
| mining-first-adaptive avgMaxDepth | 85.5 | 100.4 |
| balanced-adaptive avgMaxDepth | 79.1 | 96.6 |

一方で、貼り付きから解放され深部へ到達できるようになった副作用として、死亡数（100中）が
以下のように増加した:

| 戦略 | 修正前 deaths | 修正後 deaths |
|---|---|---|
| mining-first | 51/100 | 64/100 |
| balanced | 48/100 | 51/100 |
| mining-first-adaptive | 33/100 | 40/100 |
| balanced-adaptive | 34/100 | 32/100（変化なし程度） |
| combat-first / combat-first-adaptive | 3/100 / 4/100 | 3/100 / 2/100（ほぼ変化なし） |
| bridge-reliant | 0/100 | 0/100（変化なし） |

個別ラン（finalHp/kills/damageTaken）を確認したところ、これは新種の理不尽な即死ではなく、
従来は貼り付きによって到達できなかった深部（band境界を越えた先）で通常の被弾が蓄積して
死亡する、ありふれたパターンだった。つまり**`src/core/game.ts`の難易度カーブ自体は無変更のまま、
検証ボットが従来より深くまで到達できるようになったことで、これまで測れていなかった深部の
難易度を初めて測れるようになった**というのが妥当な解釈である。hp/atk投資を後回しにしがちな
mining-first系ほど死亡率上昇が大きく、combat優先・迂回橋優先の戦略はほぼ影響を受けていない
点も、投資判断の帰結として筋が通っている。

20シード（1〜20）の再比較では、`digging.remaining`の安全係数（×1か×2+2か）による結果への
影響が本サンプルでは検出できなかった（いずれの係数でも十分な余裕があったため）ことを確認した
うえで、より安全側の`×2+2`を採用した。

残存する貼り付き（17シード）は、掘削残りが4tick以上のケースや、そもそも燃料容量自体が
不足しているケースが原因と推定され、本回では追加修正を見送った。

## 判定

**FIX（検証ボット側の新規バグを修正。ゲーム本体は無変更で、修正の副作用として深部の難易度が
初めて可視化された）**

理由:

- 新規100シードのストレステストで、複数戦略が同時にdepth37〜43へ貼り付く経済停滞パターンを
  27件（27%）検出した。原因を`src/core/game.ts`ではなく検証ボットの帰還判断ロジックまで
  特定し、副作用を定量評価したうえで修正した
- 修正により貼り付きは大幅に減少（-37%〜-50%）し、avgMaxDepth/avgScoreも改善した一方、
  従来測れていなかった深部の難易度が死亡率上昇という形で可視化された。これは`src/core/game.ts`
  自体の新規課題ではなく、検証の精度が上がったことによる発見であり、cycle9-v1の
  「ゲーム本体に関わる新規課題は見つからなかった」という結論は今回も覆らない
- ただし、この新しく可視化された死亡率上昇（mining-first 51%→64%等）への対応要否は
  本回のスコープ（軽い追加検証）を超える判断であるため、次回（final）へ持ち越す

## Learnings（次に持ち越す学び）

- **「掘削中断で進捗がリセットされる」仕様（004由来の既知パターン）は、燃料安全マージンという
  別の帰還トリガー経由でも同じ停滞を引き起こしうる。** 004・005で確認された「HP/低燃料での
  帰還が掘削進捗を捨てる」パターンが、今回は「あと一歩で貫通する掘削を安全マージンぴったりで
  毎回中断する」という形で再発した。今後、新しい帰還トリガーを追加する際は「掘削完了間際か」を
  優先度チェックに含めることを標準パターンとして検討すべきである
- **検証ボットの精度を上げると、それまで到達できていなかった領域の難易度が新たに可視化される。**
  今回、貼り付きバグを直したことで初めてmining-first/balanced系がband境界を越えた深部の
  難易度を体験し、死亡率が大きく上昇した。これはゲーム本体の後退ではなく、単に「今まで
  測れていなかった指標が測れるようになった」だけであり、ストレステストで見つかった副作用を
  即座に「回帰」と誤判定しないよう、原因（新規到達領域か、既存領域の挙動変化か）を必ず
  切り分けるべきである
- **次サイクル（サイクル9・4回目、FINAL REVIEW）への提案**: 今回可視化された深部（depth90〜160
  台）でのmining-first/balanced系の死亡率上昇（51%→64%等）について、(a)ブラウザAIPで
  P01/P02が実際にこの深さ帯まで到達した場合の体感を確認し、(b)通常の被弾蓄積死という
  想定内の帰結か、それとも`src/core/game.ts`側のhp/atk投資と敵の深さスケーリングのバランスに
  見直しが必要かを判断したうえで、サイクル9の総括を行うことを推奨する
