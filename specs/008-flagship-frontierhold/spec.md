## 本サイクルの性質（重要）

**サイクル1〜6で要素ごとに検証してきた「面白いシステム」の発見フェーズは終わり、本サイクルからは
それらを1つのゲームへ磨き上げる統合実装フェーズに入る。** そのため本仕様書は新しい要素・新しい
コアファン仮説を追加するものではなく、007-combat-mining-building-outpostのコードベースをそのまま
土台とし、以下の1点を**本命ゲームの完成度を左右する最優先修正**として扱う：

> 007final で発見された「前線基地の建設可否判定が理論上の可否（二値）しか見ておらず、実際に
> 迂回橋代を貯めるまでの所要時間を無視している」という設計限界により、P02のブラウザセッションで
> セッションの83%（tick1000〜6000）がband境界の壁際での実質的な足踏みに費やされていた。
> この「詰みではないが詰みに近い停滞」を解消できて初めて、007までに確立した7つの共通パターン
> （常設ショップ・安全マージン公開・固定範囲保護・詰みからの脱出手段・緊急離脱・建築の第三選択肢・
> 目標を生む建築）が名実ともに「本命ゲームの土台」と呼べる状態になる。

ゲーム名 frontierhold は「前線(frontier)を保持(hold)し続けられる」という、上記の停滞解消を
指した命名。

## コアファン仮説（1行、007から継承）

> 深部で「前線基地（アウトポスト）」を建てると、そこが新しい地上（帰還先・ショップ・回復地点）になり、
> 「基地があるからもう少し深く行けそうだ」という具体的な次の一手が採掘のたびに繰り返し生まれる。
> ただし、この仮説が機能するには「基地を建てた後、次の一歩を踏み出せるまでの待ち時間」が
> 妥当な範囲に収まっていることが前提条件であり、008ではこの前提条件自体を検証・修正する。

## 008で実施した修正内容

### 修正1: `hasForwardProgressBelow()` に「待ち時間」の概念を追加（`src/core/game.ts`）

007の`hasForwardProgressBelow(y, moneyAfterCost)`は、建設地点の直下の行(y+1)全16列について
「既に通行可能」「採掘威力で突破可能」「今すぐ迂回橋代を払える」のいずれかを満たす列が1つでも
あれば建設を許可していた。しかし実際には、この判定を通過して前線基地を建てた**後**、その資金は
ショップ購入や別の用途に消費されうるため、「その時点で理論上は払えた」ことは「実際に払える」ことを
保証しない。007finalではこのギャップが「壁際に居座ったまま資金が貯まらず長時間足踏みする」個体を
生んでいた。

修正: 判定に3つ目の条件を追加した。即座に突破できない場合でも、「前線基地に居座り続けて
`LABOR_INCOME`（15tickごとに+1金）で資金を貯めた場合、最安の突破手段（迂回橋）の代金に届くまでに
かかる見込みtick数」を計算し、これが`OUTPOST_MAX_WAIT_TICKS`（400tick）以内であれば「妥当な待機」
として建設を許可する。それを超える場合は建設自体を拒否する（そもそもそこには基地を建てさせない）。

```
OUTPOST_MAX_WAIT_TICKS = 400
```

これにより、「建てたら最後、実質的に無限に足踏みする」配置を事前に防ぐ。400tickは6000tickの
ブラウザセッションの約6.7%に相当し、007finalが問題視した83%という水準からは大幅に短縮される。

### 修正2: ボットの`wallReserve`追跡バグを修正（`headless/simulate.ts`）

007 v3で導入した`wallReserve`（壁を検知した際に迂回橋代を通常購入より優先確保する仕組み）は、
「`s.phase==='mine'`のときだけ再計算し、shopフェーズでは保持する」という設計だった。しかし
実際には、壁に当たった**後、撤退のため上に戻っている最中**も`s.phase`は`'mine'`のままであり、
毎tick「現在地の1つ下の行」を再評価していた。撤退中は現在地が浅くなっていくため、既に通行済みの
浅い行（=もう壁ではない）を見て`wallReserve`が0にリセットされてしまい、基地に到着する頃には
「壁が存在した」という記憶自体が失われていた。結果、資金を貯めずに再度潜行しては同じ壁に阻まれて
即撤退する、より短い周期の往復に置き換わっていた（007final該当箇所参照）。

修正: `wallReserve`が指す「壁の行(y+1)」を`wallRow`として明示的に記憶し、実際にその行へ到達・
通過して「もう塞がれていない」と確認できるまでは`wallReserve`を保持するよう変更した。撤退中に
浅い行を見ても、その行が`wallRow`未満である限り上書きしない。

## v2で実施した修正内容（v1指摘#2対応）

v1レビュー（reviews/008-flagship-frontierhold-v1.md）で発見された「迂回橋の都度払いがdrill投資の
代替として機能しすぎ、P01・P02とも6000tickの全セッションでdrillLevelが0のまま変化しなかった」問題
（中・新規）に対応した。

### 原因

`headless/simulate.ts`の`tryBuy()`は、優先度リストの先頭から順に「money - itemCost >= reserve」を
満たす最初のアイテムを買う。drillはbaseCost30と全アイテム中最高額なうえ、`reserve`
（wallReserve+outpostReserveの合計、深部では40〜90に達する）が常に上乗せされるため、
「money - 30 >= reserve」を満たすには所持金がreserve+30まで積み上がる必要があった。しかし
迂回橋・前線基地の予約が優先的に消費するため、実測では所持金が最大でも19程度までしか育たず、
drillの初回コストに一度も届かなかった。

### 修正: drillの初回購入だけをreserveの対象から除外

`headless/simulate.ts`の`tryBuy()`に、skillの初回購入特例と同様の特例を追加した:
drillLevelが0のとき、「money >= drillCost（reserveを無視）」を満たせば無条件で最優先購入する。
2回目以降のdrill購入は通常の優先度リスト・reserveの対象に戻る。bridge-reliant戦略は
「drill投資ゼロでも壁を越えられるか」というA/B比較の検証対象であるため、この特例の対象外とした
（drillが元々優先度リストに含まれていないため実質的に無効化されたまま）。

一時的な30金の持ち出しはreserveの再蓄積を数tick遅らせるだけで、以降の壁越え・前線基地建設を
妨げないことをヘッドレスシミュレーションで確認した。

### 検証結果（20シード×5戦略、v1→v2）

| 戦略 | avgMaxDepth (v1→v2) | avgUpgradesBought (v1→v2) | deaths (v1→v2) |
|---|---|---|---|
| mining-first | 77.0 → 78.8 | 9.7 → 9.8 | 9/20 → 9/20（変化なし） |
| combat-first | 70.5 → **81.1** | 5.2 → **9.0** | 0/20 → 0/20 |
| balanced | 71.8 → 75.8 | 8.9 → 10.1 | 2/20 → 2/20 |
| bridge-reliant（対照群） | 62.8 → 62.8（不変、想定通り） | 2.6 → 2.6（不変） | 0/20 → 0/20 |
| balanced-no-outpost | 40.0 → 39.9（不変） | 5.0 → 5.0（不変） | 0/20 → 0/20 |

drillが元から優先度リストの中〜後方にあるcombat-firstで最も効果が大きく、avgMaxDepthが+15%・
avgUpgradesBoughtが+73%改善した。bridge-reliant・balanced-no-outpostは意図通り無変化で、修正が
対象戦略以外に副作用を与えていないことを確認した。mining-firstの死亡率（v1指摘#3、9/20）は
この修正の前後で完全に同一の9/20のまま変化せず、drill投資の有無とは無関係な要因（後述）である
ことが裏付けられた。

ブラウザAIPでP01(seed301)/P02(seed302)を6000tick再実行し、drillPowerが両者とも1（level0）から
上昇したことを確認した（P01: 1→4、tick1200までに3レベル購入。P02: 1→2、drillが8番目の優先度でも
1レベル購入に成功）。

## v1指摘#3の再確認（mining-first死亡率7/20→9/20）

20シードの死亡内訳（seed, maxDepth, ticks）を個別に調査したところ、死亡した9シードは全てmaxDepth
57〜160という深部（band3〜band8相当）で発生しており、生存した11シードはmaxDepth36〜160の範囲に
広く分布していた（生存シードにも最深部y=160到達が1件ある）。死亡シードの一部（seed1: ticks2289,
seed9: ticks1412）はマップ最下部(y=160、H=161の物理的な下限)まで2000〜3000tick程度という
急ピッチで到達しており、「戦略の本来の目的（採掘優先）を貫くために早期から積極的に潜り続けた
結果、対応する深さの敵の強さに見合うだけの生存力強化が追いつかなかった」自然な難易度上昇と
判断した。005final・006v2で同種の判断を行った前例、および003finalで確立した「同じ被弾数でも
ビルド次第で生死が分かれる」という本命ゲームの中核パターンとも整合するため、v2ではバランス
調整は行わないこととした。

ブラウザAIPでもこの傾向を裏付ける事例が見つかった: P01(seed301, drill最優先)はv1では6000tick
完走していたが、v2ではdrill投資により早期にmaxDepth85へ到達した結果、そこでの持久戦に
耐えきれずtick4524で死亡した（finalHp0、score447）。一方P02(seed302, hp/atk優先)はmaxDepth91
まで到達しながらも6000tick完走・finalHp180/180（満タン）だった。同じ「深部への到達」でも、
生存力を優先したビルドかどうかで結果が分かれることを両ペルソナで確認でき、drill投資の
インセンティブ回復が「進みやすさ」と「死のリスク」を両方引き上げるトレードオフとして
機能していることが分かった。

## 3回目（FIX only）で実施した修正内容（v2指摘#3対応）

v2レビュー（reviews/008-flagship-frontierhold-v2.md）で新規に見つかった「P01(seed301, drill最優先)が
v2ではdrill投資により早期にmaxDepth85へ到達した結果、生存力不足でtick4524に死亡した」指摘（重要度:
中、対応必須ではなく費用対効果で判断可）への対応。003finalが確立した「ビルド次第で生死が分かれる」
という設計意図（バランス数値そのもの）は変更せず、v2レビューが提案した2案のうち「実プレイヤー向けの
UIヒント」の方を採用した。

**変更内容**: `src/core/game.ts`に、既存の「安全マージンの数値公開」パターン（`estFuelToReturn`等、
007以来のHUD/AIP共通パターン）を踏襲した新フィールドを追加した。

- `recommendedHpForBand(band)`: そのバンドで遭遇する敵（crawler/brute加重平均、depthMult込み）の
  一撃を、同時に2体分・5発耐えられる目安の最大HPを返す純関数（`avgEnemyAtkForBand()`使用）
- `GameState.player.recommendedHp`: 現在地の深さでの目安HP
- `GameState.player.combatRiskLevel`: `'safe' | 'caution' | 'danger'`。`maxHp() / recommendedHp()`が
  1.0以上ならsafe、0.7〜1.0未満はcaution、0.7未満はdanger
- `src/render/renderer.ts`のHUDに上記を色分け表示するテキスト行を追加（危険度に応じて緑/黄/赤）

CONCURRENT_ENEMY_FACTOR（同時2体分）とSURVIVAL_HITS_TARGET（5発）は、v2で実際に死亡したP01
（band4到達時点でdrillLevel0・atkLevel0・hpLevel0のデフォルト値のまま）の組み合わせが
ちょうど`danger`判定になることを基準に較正した。ヘッドレスでバンドごとの値を検証したところ、
band0-1はsafe、band2-3はcaution、band4以降はdefaultビルドでdanger判定になることを確認した。

**このヒントはボットの購入・行動ロジックには一切接続していない**（`headless/simulate.ts`は無変更）。
20シード×5戦略のヘッドレス比較で全指標がv2から完全に不変（ゼロ差分）であることを確認済みで、
既存のバランス・A/B比較用の対照群を一切汚染しない。

**ブラウザAIPでの検証**: v2と同じくP01(seed301)/P02(seed302)の優先度でボットロジックをJS移植し
6000tick再実行した。P01はtick4524でfinalHp0/maxDepth85/score447という**v2と完全に同一の結果**で
死亡し、決定論が壊れていないことを確認した。その上で`combatRiskLevel`はtick1110（y=81、死亡の
3400tick以上前）で初めて`danger`になり、以後死亡まで`danger`/`caution`を行き来し続けていた
（`safe`に戻ることは一度もなかった）。一方P02はmaxDepth91/score409という**v2と完全に同一の結果**で
6000tick完走し、`combatRiskLevel`は6000tick全てで`safe`のまま（caution/danger共に0tick）だった。
「合理的に見えて実は高リスクなビルド」（P01）には十分早期から継続的に警告が出て、安全に生存できた
ビルド（P02）には誤検知（false positive）が一切発生しないことを両ペルソナで確認できた。
