## 本サイクルの性質（重要）

**サイクル1〜6で要素ごとに検証してきた「面白いシステム」の発見フェーズは終わり、本サイクルからは
それらを1つのゲームへ磨き上げる統合実装フェーズに入る。** そのため本仕様書は新しい要素・新しい
コアファン仮説を追加するものではなく、007-combat-mining-building-outpostのコードベースをそのまま
土台とし、以下の1点を**本命ゲームの完成度を左右する最優先修正**として扱う：

> 007final で発見された「前線基地の建設可否判定が理論上の可否（二値）しか見ておらず、実際に
> 迂回橋代を貯めるまでの所要時間を無視している」という設計限界により、P02のブラウザセッションで
> セッションの83%（tick1000〜6000）がband境界の壁際での実質的な足踏みに費やされていた。
> この「詰みではないが詰みに近い停滞」を解消できて初めて、007までに確立した7つの共通パターン
> （常設ショップ・安全マージン公開・固定範囲保護・詰みからの脱出手段・緊急離脱・建築の第三選択肢・
> 目標を生む建築）が名実ともに「本命ゲームの土台」と呼べる状態になる。

ゲーム名 frontierhold は「前線(frontier)を保持(hold)し続けられる」という、上記の停滞解消を
指した命名。

## コアファン仮説（1行、007から継承）

> 深部で「前線基地（アウトポスト）」を建てると、そこが新しい地上（帰還先・ショップ・回復地点）になり、
> 「基地があるからもう少し深く行けそうだ」という具体的な次の一手が採掘のたびに繰り返し生まれる。
> ただし、この仮説が機能するには「基地を建てた後、次の一歩を踏み出せるまでの待ち時間」が
> 妥当な範囲に収まっていることが前提条件であり、008ではこの前提条件自体を検証・修正する。

## 008で実施した修正内容

### 修正1: `hasForwardProgressBelow()` に「待ち時間」の概念を追加（`src/core/game.ts`）

007の`hasForwardProgressBelow(y, moneyAfterCost)`は、建設地点の直下の行(y+1)全16列について
「既に通行可能」「採掘威力で突破可能」「今すぐ迂回橋代を払える」のいずれかを満たす列が1つでも
あれば建設を許可していた。しかし実際には、この判定を通過して前線基地を建てた**後**、その資金は
ショップ購入や別の用途に消費されうるため、「その時点で理論上は払えた」ことは「実際に払える」ことを
保証しない。007finalではこのギャップが「壁際に居座ったまま資金が貯まらず長時間足踏みする」個体を
生んでいた。

修正: 判定に3つ目の条件を追加した。即座に突破できない場合でも、「前線基地に居座り続けて
`LABOR_INCOME`（15tickごとに+1金）で資金を貯めた場合、最安の突破手段（迂回橋）の代金に届くまでに
かかる見込みtick数」を計算し、これが`OUTPOST_MAX_WAIT_TICKS`（400tick）以内であれば「妥当な待機」
として建設を許可する。それを超える場合は建設自体を拒否する（そもそもそこには基地を建てさせない）。

```
OUTPOST_MAX_WAIT_TICKS = 400
```

これにより、「建てたら最後、実質的に無限に足踏みする」配置を事前に防ぐ。400tickは6000tickの
ブラウザセッションの約6.7%に相当し、007finalが問題視した83%という水準からは大幅に短縮される。

### 修正2: ボットの`wallReserve`追跡バグを修正（`headless/simulate.ts`）

007 v3で導入した`wallReserve`（壁を検知した際に迂回橋代を通常購入より優先確保する仕組み）は、
「`s.phase==='mine'`のときだけ再計算し、shopフェーズでは保持する」という設計だった。しかし
実際には、壁に当たった**後、撤退のため上に戻っている最中**も`s.phase`は`'mine'`のままであり、
毎tick「現在地の1つ下の行」を再評価していた。撤退中は現在地が浅くなっていくため、既に通行済みの
浅い行（=もう壁ではない）を見て`wallReserve`が0にリセットされてしまい、基地に到着する頃には
「壁が存在した」という記憶自体が失われていた。結果、資金を貯めずに再度潜行しては同じ壁に阻まれて
即撤退する、より短い周期の往復に置き換わっていた（007final該当箇所参照）。

修正: `wallReserve`が指す「壁の行(y+1)」を`wallRow`として明示的に記憶し、実際にその行へ到達・
通過して「もう塞がれていない」と確認できるまでは`wallReserve`を保持するよう変更した。撤退中に
浅い行を見ても、その行が`wallRow`未満である限り上書きしない。

### 検証結果（20シード×5戦略のヘッドレス比較、007final→008）

| 戦略 | avgMaxDepth (007final→008) | avgTrips (007final→008) | deaths (007final→008) |
|---|---|---|---|
| mining-first | 71.1 → **77.0** | 145.7 → 130.1 | 7/20 → 9/20 |
| combat-first | 41.6 → **70.5**（band1境界の壁を初めて突破） | 217.2 → 121.2 | 0/20 → 0/20 |
| balanced | 68.8 → 71.8 | 207.6 → 199.8 | 2/20 → 2/20 |
| bridge-reliant | 42.9 → **62.8**（同上） | 202.3 → 127.5 | 4/20 → 0/20 |
| balanced-no-outpost（対照群） | 39.9 → 40.0（変化なし、想定通り） | 236.4 → 233.4 | 0/20 → 0/20 |

**combat-first・bridge-reliantが、002〜007の全サイクルを通じて一度も破れなかった「band1境界
（depth40付近）の壁」を初めて明確に突破した。** これは002〜007を通じて繰り返し指摘されてきた
「進行を止める壁を他の項目と同列優先度で並べると投資が後回しになり続ける」問題（005・006final等）
が、待ち時間を考慮した建設可否判定＋ボットの壁記憶の正確化という2つの修正の組み合わせで、
少なくともヘッドレス検証の範囲では構造的に解消されたことを示す。avgTripsも全戦略で改善（往復の
無駄が減少）。mining-firstの死亡がやや増加(7→9/20)しているが、これは到達深度が伸びたことに伴う
自然な難易度上昇と考えられ（005final・006v2で同種の判断を行った前例に倣う）、v1レビューで
ブラウザAIPの結果と合わせて最終判断する。
